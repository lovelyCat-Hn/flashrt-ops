# 问题-解决：闭环执行抖动与 RTC 执行侧修复

**机型**：galbot-echo（本机，第三台）｜ **链路**：pi0.5 (FlashRT bf16, CUDA graph) →
GalbotSDK `set_joint_positions` 刚性位置伺服 ｜ **脚本**：`scripts/inference/run_g1_loop_rtc.py`
（B 脚本，`run_g1_loop.py` A 脚本逐行同源）｜ **写作日期**：2026-10-08

---

## 0. 一句话结论

闭环执行链路上出现过**两个独立的抖动问题**、动了**两刀**：
①指令边界换向抖动 → **自研 v4 追踪式配速**（2026-09-24，与 lerobot 无关）；
②深尾续航往复摆臂+夹爪翻摆 → **参照 lerobot/PI RTC 只移植执行侧调度层**（RTC hold，
2026-10-04 定案）。lerobot RTC 的**推理侧去噪引导（denoise_step 前缀引导）未采用**，
原因见 §5（CUDA graph / autograd / 延迟≈1 轮 / ckpt 未做 RTC 训练 / 调参风险，五条）。

---

## 1. 背景：链路与时间参数

receding-horizon 闭环：模型每轮输出 **chunk = 50 步 @30fps 语义（≈1.67 s）**，
执行侧每轮只消费配额 **n_steps = 20~25 步（≈0.67~0.83 s）**，剩余步"留在地上"
给迟到的推理兜底。关键时间量（v3 工作点实测，见 BENCHMARKS §七）：

| 量 | 数值 | 说明 |
|---|---:|---|
| 单轮推理 p50 | 329 ms（真机闭环，nav-suspend；SDK 全栈在场 375 ms） | 与上轮执行重叠，理论上零等待（BENCHMARKS 表 1-1） |
| 执行窗（pace） | 0.35 s/指令窗 | 每窗发一条限速位置指令 |
| 配额消费完 → 新块就绪 | 需 ≤0 | 推理若迟到即产生"空洞" |
| **水位（waterline）** | pace ≈0.34~0.35 | 推理延迟可被完全藏住的 pace 下限；压破即出空洞 |

空洞怎么填，就是这个文档的全部故事：**喂旧块深尾（A，出问题）vs hold 等待（B，修复）**。

## 2. 问题一：指令边界换向抖动（2026-09-24，自研修复）

### 现象
早期步进式执行（每步一条指令、`is_blocking=True` 阻塞到位再发下一条）下，
臂在每个指令窗末尾**速度过零**；下一窗目标若与前窗残余导程方向相反，臂在边界处
**换向抽动**，速度曲线呈锯齿（"卡卡的"）。

### 根因
"到点再走"的停走节奏 + 指令边界处速度不连续。位置伺服把每条指令都走满，
边界即速度零点；抖动 = 换向 × 零点，两个都有就触发。

### 修复：v4 追踪式配速（自研）
```python
pace_v = max(V_MIN, min(导程 / (div × pace), speed))   # 每窗按比例走导程
robot.set_joint_positions(tgt, speed_rad_s=pace_v, is_blocking=False)
```
- **div 比例走导程**：div=2 即每窗走一半导程（v3 工作点 div=1.5 → 走 2/3）→ 臂恒在途、
  永不到点 → 速度不过零 → 无换向点；下一窗从**真实读数**重算导程，滞后自校正
  （闭环每轮重规划天然容错）
- 速度是导程的比例项：导程大自动快、趋零自动慢，边界连续无锯齿
- 近距阻尼（`--near-div/--near-gap`）：导程 <60 mrad 时降速，收敛单调不振荡

**修复日期 2026-09-24，与 lerobot RTC 无关**——这是纯执行器设计。此修复后残留的
抖动问题全部来自 §3 的深尾路径。

> 旁注：另一条已封存路线（PVT 轨迹下发，`chunk_mode="traj"`）有**不同**的抖动病
> （每点全停、冲击∝速度，零运动探针也抖），与本问题无关，见
> `scripts/probes/g1_traj_probe.py` 留档。本文其余部分全部针对 track 指令流。

## 3. 问题二：深尾续航往复摆臂 + 夹爪翻摆（2026-09-30 实录）

### 现象
A 脚本（当时唯一变体）在 pace 压到水位附近/以下时（9/30 sweep 0.40/0.38，
`logs/loop_20260930_*.log` 六跑）：配额消费完而推理未归，执行侧**继续喂旧 chunk
的第 20~49 步（深尾）续航**——臂开始**前后往复摆动**，夹爪在开/合之间**来回翻摆**，
越跑越乱。9/30 的"0.40 破位 / 0.38 判死"结论**只属于这条深尾路径**，不是模型或
配速律的问题。

### 根因剖析：深尾是"计划垃圾"
chunk 第 k 步是基于**规划瞬间的观测**对 t₀+k/30 s 世界的预测。执行侧每 ~0.35 s
重规划一次，真实世界每轮都在修正：

1. **时间错位**：深尾步（20~49 步 ≈ 规划后 0.67~1.67 s）执行时，真实状态已被
   此前 2~4 轮的执行改写。旧计划假设"前 20 步被精确执行"，但追踪式配速刻意
   **每窗只走半程**——真实位置系统性落后于旧计划的位置，深尾指令相对真实状态
   变成**超前的、可能反向的**目标。
2. **衰减/反转**：模型长时程预测本身衰减；反馈回路缺失的尾段一旦与真实状态
   反号，位置伺服每窗忠实执行反向目标 → **往复摆臂**。
3. **夹爪翻摆**：深尾行里的夹爪目标在旧计划里本就随任务摆动，尾段反复重发，
   chg 阈值拦不住（相邻深尾行目标本来就不同）→ **开合翻摆**。

一句话：**深尾 = 无反馈的开放环开环执行**，闭环里喂它等于把系统降级成开环。

## 4. 修复：RTC 执行侧调度层（B 脚本，2026-10-04 定案）

### 出处与移植范围
- **参照**：Physical Intelligence *Real-Time Chunking* 论文 +
  lerobot `src/lerobot/policies/rtc/modeling_rtc.py`（Apache-2.0，`RTCProcessor`）。
  **机制级参照，非逐行移植**——我们的执行器是限速位置指令流，与 lerobot 的
  策略采样循环结构不同，调度约定按我们的指令流重新实现。
- **只搬执行侧调度层**（推理迟到时执行侧怎么过渡）；**未搬推理侧去噪引导**
  （`denoise_step` 前缀引导），原因 §5 详述。

### RTC hold 机制四要素（B 脚本默认行为）
配额消费完而推理未就绪时：

| # | 机制 | 代码行为 | 治什么 |
|---|---|---|---|
| 1 | **单调收敛 hold** | `tgt_h = cur + clip(已消费段终点 − cur, ±BUDGET)`，逐窗几何逼近 | 永不过冲 → **不可能反向** → 往复从数学上被排除 |
| 2 | **轮询早退** | 10 ms 轮询推理 job，一落地立即换块（不烧满剩余窗） | hold 只产生纯墙钟成本，**永不喂一步垃圾** |
| 3 | **夹爪行冻结** | hold 窗统一发已消费段终点行（`chunk[n_steps-1]`），chg 阈值自然抑制重发 | 同值重发被拦 → **不翻摆** |
| 4 | **护栏全时生效** | 漂移护栏/限幅/配速律照旧 | hold 不放大行程风险 |

可选坡升 `--rtc-ramp N`：hold 连续 ≥2 窗（臂真减速过）后，N 轮臂速按
0.5→1.0 线性恢复——对应 lerobot/论文执行侧 blend/crossfade，柔化再起步。
hold 仅 1 窗即被早退接走（臂未真减速）时不触发，避免慢性拖慢。

### 与 A 的对照开关
`--no-rtc-hold` 在 B 脚本内退回 A 的深尾行为，专为 A/B 对照保留；
`--rtc-hold-max 6`（默认）为推理挂死保护（连续 6 窗未归判挂死停循环）。

### 为什么能根治往复（数学性质）
深尾路径往复的充要条件是"指令目标序列相对真实状态反向"。hold 的目标序列
`{cur_k}` 满足 ‖tgt_h − cur_k‖ 单调不增（每窗只向已消费段终点走被 BUDGET 限幅的
一步），**方向恒指向同一目标**——反向指令在结构上不存在。夹爪同理（目标恒定）。

### 验证（2026-10-04 主对照）
- **A/B 对照 14 跑全绿**（`logs/loop_20261004_*.log`）：同参数下稳态行为一致
  （零 hold）；pace 压到水位下时 A 出深尾垃圾、B 平滑退化（hold=纯等待）。
- 工作点定案：**v2 = spc25/pace0.38/div1.65（1.33×）**，每轮都有 hold 窗仍
  R 落盒 14.0~14.5 s 纪录；10-07 加 `--nav-suspend`（推理水位上行 ~55 ms）后
  **v3 = 25/0.35/1.5（1.59×），hold 窗 0（两跑 76 轮）**，R 落盒 10.0 s。
  数据见 BENCHMARKS §七 表 7-1/7-2。

### hold 的现状定位
v3 下推理已藏得住，hold 窗归零——**执行侧调度层的日常价值已退化为保险**：
pace 再压、推理偶发毛刺、或未来换更大模型时，它是"宁可慢下来也不喂垃圾"
的兜底，这正是 RTC 论文对推理滞后 (inference lag) 处置的核心承诺。

## 5. 为什么只搬执行侧——推理侧（denoise_step 前缀引导）不采用的原因

lerobot/PI RTC 完整结构是两半：
- **推理侧**：`RTCProcessor.denoise_step(x_t, prev_chunk_left_over, ...)`——把上一块
  未执行的尾段 (prev_chunk_left_over) 作为前缀，在每个 ODE 去噪步计算
  `x1_t = x_t − time·v_t`，对 `(prefix − x1_t)·weights` 做 **autograd 穿整网回传**，
  得到校正项 `v_t − w·correction`（权重 `get_prefix_weights` 调度 + `max_guidance_weight`
  钳位）；作用是让新块开头与旧块未执行部分**衔接连续**，从源头消块间跳变。
- **执行侧**：推理滞后期间的调度约定（本文 §4 移植的部分）。

不采用推理侧的五条原因（2026-10-04 评估，按权重排序）：

| # | 原因 | 说明 |
|---|---|---|
| 1 | **与 CUDA graph 捕获冲突** | `denoise_step` 必须逐 ODE 步插入 Python 回调；我们的推理栈靠整图捕获（较 eager 省 ~17 ms，表 1-3，且是现役 W8A16 kernel 路线的地基）。图内没有逐步 Python 钩子的位置——要么弃图（全链路 eager 化），要么把引导融合进图（每档 prefix 长度一张图，工程量与爆图风险大） |
| 2 | **autograd 穿整网** | 校正项梯度要穿整个去噪网络（源码 `torch.autograd.grad(x1_t, x_t, …)` 且 `torch.enable_grad()`）。推理态 no_grad/CUDA graph 下不可用；强行开需保留反向图，单步显存与算力代价约翻倍，且 W8A16 量化 kernel 路径不带 autograd |
| 3 | **本链路 delay≈1 轮，收益趋零** | RTC 引导治的是"滞后大 → 新旧块接缝跳变"。我们的闭环把推理藏在执行窗里（v3 实测 hold 窗 0，76 轮），接缝跳变的来源（滞后）本身≈0——引导没有可校正的对象，纯增开销 |
| 4 | **ckpt 不具备 trained 模式** | lerobot RTC `mode="trained"` 要求 `rtc_training_max_delay>0` 训练的 checkpoint（`trained_mode_supported=False` 直接 raise）；pi05_g1_* 是常规微调产物，只能走零样本引导模式，而该模式又受 #1~#3 制约 |
| 5 | **新增超参与回归风险** | prefix 权重调度、`max_guidance_weight`、`execution_horizon` 均需在真机上重新调；为一个当前不存在的问题给已验证闭环引入不可控变量，收益/风险不成立 |

**什么情况下应重评**：若未来推理延迟上到与执行窗同量级（更大模型/多任务串联）、
或放弃 CUDA graph、或 ckpt 按 RTC 训练——届时 #1~#4 逐条解除，再评估引导层。
